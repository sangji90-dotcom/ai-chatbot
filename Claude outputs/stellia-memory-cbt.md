검증: **pytest 56개 통과**(43 → 56), FE `tsc` 에러 0, 실 `.env` 기동 성공(라우트 152개), 정합성 점검 통과.

## 출발점: 그 기능은 한 번도 실행된 적이 없었다

실DB 확인 결과 — `memory_book` **0행**, 최장 세션 **2턴**, `message_ratings` **0행**.

원인이 넷이었고 전부 고쳤다.

| # | 문제 | 결과 |
|---|---|---|
| 1 | 자동 추출이 **메모리 패스(유료) 보유자 전용** | CBT 테스터는 아무도 해당 없음 → 검증 대상이 꺼진 채로 테스트 |
| 2 | "10턴마다"가 아니라 **10번째 턴의 1쌍만** LLM에 전달 | 2턴째에 말한 이름은 영영 기록 안 됨 |
| 3 | `memory_chunk_limit`이 **결제에만 쓰이고 주입엔 무제한** | 프롬프트 무한 증가 + 오래된 기억이 최신을 밀어냄 |
| 4 | 웹에 **메시지 평가 UI가 아예 없음** | `/chat/rating` API는 있는데 호출하는 곳이 없어 피드백 0건 |

## 변경 내용

### 1. 게이팅 해제 — `MEMORY_FOR_ALL=1`

전원에게 자동 기억을 연다. 유료화 시점에 이 값만 `0`으로 돌리면 메모리 패스 전용으로 복귀.

### 2. 추출이 구간 전체를 본다

```python
await extract_memory(..., working[-MEMORY_EXTRACT_EVERY:], ...)   # 직전 10턴 전체
```

추출 프롬프트에 **이미 저장된 기억 목록을 함께** 넘겨서 "아는 건 빼고 새로운 것만" 뽑게 했다. 같은 기억이 반복 적재되면 프롬프트만 커지고 정확도는 떨어진다.

파싱도 정리: 불릿/번호 제거, 120자 초과 폐기, 정규화 비교로 중복 제거, 회당 최대 3개.

### 3. 주입 상한 실제 적용

`chat/memory.py`의 `load_memories()`가 **최신 우선으로 N개**만 가져온다(무료 20, 패스 보유자는 구매한 만큼). 원본은 지우지 않고 주입만 제한하므로 나중에 상한을 올리면 과거 기억이 되살아난다.

### 4. 계측 — `memory_events` 테이블

| 이벤트 | 의미 |
|---|---|
| `inject` | 요청당 주입된 기억 수. 계속 상한에 붙어 있으면 상한이 병목 |
| `extract` / `extract_empty` / `extract_fail` | 추출 시도 대비 실제 적재 비율 |
| `summarize` / `summarize_fail` | 요약 발동·실패. 요약 이후 신고가 늘면 요약이 범인 |
| `reported_forgot` | 유저가 **직접** "기억 못한다"고 누른 것. 가장 직접적인 신호 |

### 5. 신고 사유 태그

`message_ratings.reason` 컬럼 추가. dislike가 기억 문제인지 말투 문제인지 구분되지 않으면 기억 품질을 측정할 수 없다.

웹에 **`MessageFeedback` 컴포넌트를 새로 만들어 붙였다** — AI 메시지마다 👍/👎, 👎를 누르면 사유 칩이 뜬다:

> 앞서 한 얘기를 기억 못해요 · 같은 말을 반복해요 · 말투가 캐릭터랑 안 맞아요 · 엉뚱한 소리를 해요 · 너무 짧거나 성의 없어요 · 기타

`Message.messageId`(서버 `chat_history.id`)를 응답에서 받아 보관하도록 `ChatApp`도 수정.

### 6. 관리자 대시보드 API

```
GET /admin/memory-stats?days=7
GET /admin/memory-stats/samples      # 신고된 메시지 + 전후 맥락 + 그 시점 보유 기억
```

`samples`가 실제 원인 분석용이다. "기억 못한다"고 신고된 메시지의 직전 6턴과, **그때 실제로 주입돼 있던 기억 목록**을 함께 보여준다. 추출이 안 된 건지, 추출은 됐는데 AI가 안 쓴 건지, 상한에 밀린 건지가 여기서 갈린다.

## E2E 시뮬레이션 결과 (가짜 LLM, 21턴)

```
턴 10: 응답10 (아는이름:지훈)     ← 2턴째 "내 이름은 지훈이야" 가 추출돼 주입됨
턴 11: 응답11 (아는이름:지훈)
턴 20: 응답20 (아는이름:지훈)

LLM 호출 — 대화: 20 / 추출: 4
저장된 기억: ['유저의 이름은 지훈이다', '유저는 고양이를 키운다', '유저는 야근이 잦다']
계측: extract 2회(평균 1.5) / extract_empty 2회 / inject 20회(평균 2.0)

/admin/memory-stats
  세션 분포: {under_10: 0, turns_10_40: 1, turns_40_100: 0, over_100: 0, avg_turns: 21.0}
  추출 성공률: 0.5        ← 중복 방지가 작동해 후반 2회는 빈 추출
  요청당 주입 기억 수: 2.05
  '기억 못함' 신고: 1
```

**핵심**: 2턴째 정보가 10턴째 추출에서 잡혔다. 구 구조(10번째 턴 1쌍만)에서는 절대 잡히지 않던 케이스다.

## CBT에서 볼 지표

| 지표 | 읽는 법 |
|---|---|
| `sessions.turns_10_40` 이상 비율 | **10턴을 못 넘기면 기억이 작동할 기회 자체가 없다.** 이게 낮으면 기억 이전에 대화 재미를 먼저 봐야 함 |
| `extract_rate` | 0.2 미만 = 추출 프롬프트가 너무 보수적. 0.9 이상 = 쓸데없는 것까지 줍는 중 |
| `avg_injected` vs 상한(20) | 계속 20에 붙어 있으면 상한이 병목 → 올리거나 중요도 선별 필요 |
| `forgot_reports` / 총 AI 메시지 | **가장 중요한 단일 지표.** 이게 떨어지면 개선이 먹힌 것 |
| `summarize` 발동 후 `forgot_reports` 증가 | 요약이 기억을 깎아먹는 중 → `AUTO_SUMMARY_THRESHOLD` 조정 |

전부 환경변수로 조절 가능하니 CBT 중에 재배포 없이 실험할 수 있다:

```
MEMORY_FOR_ALL=1          # 유료화 시 0
MEMORY_EXTRACT_EVERY=10   # 추출 주기
MEMORY_FREE_CHUNKS=20     # 무료 주입 상한
AUTO_SUMMARY_THRESHOLD=100
RECENT_TURNS_KEPT=40
```

## 남은 판단

- **요약 임계값 100턴은 아직 손대지 않았다.** 요약은 기억을 늘리는 게 아니라 압축하는 장치라 값을 낮추면 손실이 커진다. Gemini의 컨텍스트가 넉넉하니 지금은 계측만 하고, `summarize` 발동 후 `forgot_reports`가 실제로 오르는지 보고 조정하는 게 맞다.
- **Flutter 앱엔 피드백 UI를 안 붙였다.** 웹으로 먼저 데이터를 모으고, 사유 목록이 확정되면 그때 붙이는 게 덜 번거로움. API(`GET /chat/rating/reasons`)는 이미 열어뒀다.
- 관리자 화면(`AdminPage.tsx`)에 지표 탭은 아직 없음. API를 직접 호출해도 되고, 필요하면 붙여줄게.
